# SakuttoSeat v2.1 要件定義書

**人数・会場サイズの上限と、リワード広告（会場拡張）の統合**  
対象バージョン: **2.1.x**（現行は 2.0.0）  
位置づけ: 実装前の仕様。クラッシュ防止とマネタイズを両立する。  
前提: `docs/v2.1_ExportAndPresentation.md` の発表モード／共有拡張とは独立。本仕様は入力と会場サイズだけを扱う。

---

## 0. 目的・概要

「サクッと」の価値は速さそのもの。教員の学級席替え（35〜40人）と幹事の小宴会は、**今までどおり広告なしで完了**させる。その外側だけを、1本の動画で広げる。

入れる理由は2つで、優先順位はこの順です。

1. **クラッシュ防止**  
   人数・テーブル数・会場列に上限がない。座席表は卓カード＋席グリッド＋書き出し用スナップショットを同時に持つ。大量データはメモリ不足と UI 崩壊（横スクロール、重なり、書き出し失敗）を起こす。
2. **収益化**  
   上限解放をリワード広告のインセンティブにする。ただし列・行・人数で動画を分けない。同じ席決めの途中で同種の動画を2回見せると離脱する。

やらないこと:

- 無料利用中に「38/40」のようなカウンタやプログレスを出さない
- 列・行・卓・人数を別商品にして、それぞれ動画を取らない
- 絶対上限の先に「もう1本見れば増える」を置かない（クラッシュラインを課金しない）
- 画像共有・お気に入り4枠目を、会場拡張のフラグに混ぜない

1回の席決めあたりの動画は **0〜2本** が上限。

| 本数 | いつ | フラグ |
|---|---|---|
| 0 | 学級40人・2列・10卓（大半の日常） | なし |
| 1 | 41人目、3列以上、11卓目、6行目のいずれか最初の1回 | `FeatureUnlockState`（会場拡張） |
| +1 | 画像を持ち出す人だけ | Share 側（本仕様の対象外） |

## 1. しきい値の定義

数値の単一定義は `FeatureLimit`（`nonisolated enum`）。View にマジックナンバーを書かない。Interactor だけが参照する。

### 1.1 公開する上限

| 寸法 | 定数（追加） | 無料上限 | 絶対上限 | 備考 |
|---|---|---:|---:|---|
| 参加者 | `freeAttendeeCount` / `maxAttendeeCount` | **40** | **120** | 小中高の1学級が35〜40。日常の席替えを踏ませない。120は学年3クラス相当。それ以上は入力時点で「サクッと」が壊れる |
| 会場の列 | `freeColumnCount` / `maxColumnCount` | **2**（現行） | **10**（現行の `selectableRange`） | 既出荷。教室の6列はここに乗る。4列超で既に横スクロール。10超は UI 崩壊 |
| テーブル数 | `freeTableCount` / `maxTableCount` | **10** | **40** | 定員4なら無料ちょうど40席。絶対40卓は「1人1卓の教室」まで |
| 会場の行 | `freeRowCount` / `maxRowCount` | **5** | **10** | 2列×5行=10卓。行スライダーを足す場合の上限。**単独の課金商品にはしない** |

現行 `FeatureLimit` のまま残すもの（本仕様で変えない）:

- `freeTemplateCount = 3`
- `freeFavoriteGroupCount = 3`
- `freeColumnCount = 2`

列の絶対上限 10 は、現行 `VenueSettingsInteractor.selectableRange = 1...10` と一致させる。`maxColumnCount = 10` を `FeatureLimit` に上げ、ピッカー範囲もそこから取る。

### 1.2 内部キャップ（UI に出さない）

クラッシュを止める本物のラインは人数より **描画セル数**。

| 定数（追加） | 値 | 意味 |
|---|---:|---|
| `maxTotalSeatCount` | **160** | `Σ(各テーブルの capacity)` の上限 |

判定:

```
追加後の総席数 = 既存テーブルの定員合計 + 追加しようとしている定員
追加後の総席数 > FeatureLimit.maxTotalSeatCount なら拒否
```

このキャップはユーザー向け文言に出さない。表面に出るのは「これ以上は追加できません」だけ。  
実効上限は「人数120」「テーブル40」「総席数160」のうち先に当たった方。例: 40卓×定員4=160で総席数が先に止まる。

### 1.3 行数の扱い

現状、行は設定項目ではなく `ceil(テーブル数 / 列数)` で決まる。

- v2.1 で行スライダーを会場設定に足す場合: 列と同じ「会場拡張」フラグで開く。無料は5行、絶対は10行
- 行スライダーを足さない場合でも、テーブル追加の無料判定は `freeTableCount` で行う。行を独立して課金しない
- 行だけ sequential に課金すると、「列を増やせば行が減る」回避が生まれる。禁止

### 1.4 解放後の上限

動画1本で、無料の次から絶対上限まで一気に開く。

- 人数: 41...120
- 列: 3...10
- テーブル: 11...40
- 行: 6...10（行設定を入れる場合）

40→80でもう1本、は禁止。絶対上限に達したら広告 CTA を出さない。

### 1.5 教室レイアウト（個人机）

デフォルトは定員4の宴会卓。教員が「机1つ＝テーブル1つ・定員1」で6列教室を組むと40卓必要。

- 3列以上は現行どおり、最初の動画で開く
- **同じ1本でテーブル40・行10・人数120まで開く**（2本目を取らない）
- 無料テーブルは10のまま。宴会は無料完結。教室の6列化だけが動画

## 2. 会場拡張（セッション解放）

### 2.1 フラグの意味変更

現行 `FeatureUnlockState.isSessionUnlocked` は「3列以上の列解放」。これを **会場サイズ一式の解放** に拡張する。フラグを増やさない。列専用の新しい Bool を足さない。

| 項目 | 仕様 |
|---|---|
| 型 | 現行どおり `FeatureUnlockState`（`FeatureUnlockGateway`） |
| 共有インスタンス | 現行どおり `SessionFeatureUnlock.shared` |
| 寿命 | アプリ起動中のみ。画面 pop 後も同一プロセスなら維持。キルで消える |
| 永続化 | しない（`UserDefaults` に書かない） |
| 付与 | `grantSessionUnlock()` 成功時のみ。視聴キャンセル / 未獲得 / 失敗では立てない |

コメントを更新する。

- `FeatureUnlockGatewayImpl.swift`: 「アプリ起動中だけ有効な**列数**解放状態」→「アプリ起動中だけ有効な**会場サイズ**解放状態」
- `UnlockRequirement` のコメント: 「列数変更や画像共有」のままでよい。値は `none | rewardedAd` の2値を維持する。ハードキャップ用の case は足さない

### 2.2 要否判定（Interactor）

広告要否は Interactor だけが決める。View / Presenter は `UnlockRequirement` を見て分岐する。SDK の `isReady` は見ない。

判定順（追加・適用の直前）:

1. 絶対上限または内部キャップを超える → **拒否**。`UnlockRequirement` は返さない。Presenter はハード上限アラートへ
2. 無料上限以内 → `.none`。すぐ実行
3. 無料を超え、絶対上限以内、かつ `isSessionUnlocked == false` → `.rewardedAd`
4. 無料を超え、絶対上限以内、かつ `isSessionUnlocked == true` → `.none`

対象操作と判定対象:

| 操作 | 見る値 | 無料 | 絶対 |
|---|---|---:|---:|
| 参加者の1件追加 / 一括追加 / お気に入り読込 | 追加後の人数 | 40 | 120 |
| 会場設定の列を適用 | 選択列数 | 2 | 10 |
| 会場設定の行を適用（入れる場合） | 選択行数 | 5 | 10 |
| テーブル追加 | 追加後のテーブル数、および追加後の総席数 | 10 | 40 / 160 |

`SeatingChartInteractor.columnCountChangeRequirement(for:)` は、列専用のまま残さず、会場拡張の判定に寄せる。人数・卓用の同型メソッドを各 Interactor に足してよい。ただし中身は同じフラグを見る。

### 2.3 1本で開く範囲

どの操作で動画を見ても `grantSessionUnlock()` は同じ。成功後は、そのセッション中に次のすべてが広告なしになる。

- 人数 41...120
- 列 3...10
- テーブル 11...40
- 行 6...10（行設定を入れる場合）

コピーだけ操作に合わせて変える。フラグは共通。

| 発火操作 | ダイアログ題 | 主ボタン |
|---|---|---|
| 41人目（または一括／お気に入りで溢れる） | 人数を増やせます | 動画を見て追加する |
| 3列以上の適用 | 会場を広げます | 動画を見て広げる |
| 11卓目の追加 | 会場を広げます | 動画を見て広げる |
| 6行以上の適用（入れる場合） | 会場を広げます | 動画を見て広げる |

計測（任意だが推奨）: 「1本目がどの操作で発火したか」（人数 / 列 / 卓 / 行）。列が9割なら無料列を3に上げる判断に使う。人数発火が無いのに無料人数を下げない。

### 2.4 混ぜてはいけないリワード

| 現在 | 仕事 | 頻度 | 本仕様 |
|---|---|---|---|
| 3列以上 | 会場を広げる | セッション1回 | **人数・行・卓をここに吸収** |
| 画像共有（および v2.1 の高画質・CSV） | 成果物を持ち出す | Share モジュール側 | **独立。`FeatureUnlockState` を共有しない** |
| お気に入り4枠目 | 名簿を永続化する | 1回限りバイパス | **独立。`grantOneTimeFavoriteSaveBypass()` のまま** |

理由:

- 画像は「作り終わったあとの持ち出し」。入力中の会場拡張と口座が違う
- お気に入りは「来週も使う名簿」。セッション解放に混ぜると「動画を見たのに4件目が保存できない」が起きる
- テンプレート保存3件上限も本仕様では触らない（広告で解放しない）

### 2.5 番号札モード

参加者上限は番号札にも同じリストで適用する。テーブル・列・行の上限は座席表だけ。

## 3. UI/UX ルール

サクッとを壊すのは上限そのものではなく、**入力の手を止める長さ**。

### 3.1 原則

1. 無料中は上限の存在を見せない。カウンタ「38/40」、プログレスバー、残数キャプションは出さない
2. 解放可能な上限ではボタンを殺さない。押せて、理由が1呼吸で分かる
3. 動画成功後は、押そうとした操作をそのまま完了する
4. 絶対上限では再生ボタンを出さない。「見れば増える」と嘘をつかない
5. シートは medium 1枚、ボタンは2つまで。チェックボックスも利用規約も不要
6. 未準備は既存 `RewardedAdCopy.notReadyTitle` / `notReadyMessage` を使い回す

禁止コピー: 「上限に達しました」（エラーに聞こえる）、「プレミアム機能」、「広告を見てください」（命令）。

現行 VenueSettings の「3列以上はアンロックが必要です」は、会場側のトーンを「広げます」に寄せて人数側と揃える。

### 3.2 参加者リストの＋

| 状態 | 見た目 | タップ |
|---|---|---|
| 1...39人 | 現行の青いつぶ | 即追加 |
| 40人・未解放 | つぶは押せる。色は `secondary`。右下に小さな `play.rectangle.fill` | 人数解放ダイアログ |
| 40...119人・解放済 | 現行の青いつぶ | 即追加 |
| 120人 | つぶは半透明（opacity 約 0.35）で disabled | ハード上限アラート（再生なし） |

名前入力中に40人へ到達しても、フィールドの値は消さない。

### 3.3 一括追加・お気に入り読込

貼った名前／グループを捨てない。

1. 追加後人数が無料以内、または解放済で絶対以内 → 全部入れる
2. 未解放で無料を跨ぐ → 無料枠まで先に入れ、溢れた行はバッファに残す。ダイアログで残り人数を案内。成功後にバッファを流し込む
3. 絶対上限を跨ぐ → 絶対上限まで入れ、残りは入れない。ハード上限アラート。溢れを黙殺しない

例: 現在40人・未解放で20人を貼る。

> 20人中、あと0人まで無料です。動画を1本見ると残りも追加します。

成功後、バッファ20人を追加（合計60）。絶対120を超える分だけ切り、その旨をハード上限で伝える。

お気に入り45人グループの読込も同じ。40人で切って黙殺しない。

### 3.4 テーブル追加

座席表キャンバスの「テーブル追加」カード。

| 状態 | 見た目 | タップ |
|---|---|---|
| 1...9卓 | 現行の破線＋プラス | 即追加 |
| 10卓・未解放 | 同じカードに再生バッジ | 会場拡張ダイアログ |
| 10...39卓・解放済 | 現行カード | 即追加 |
| 40卓、または総席数160に到達 | カードを出さない。末尾に小さなキャプション「テーブルは40まで」 | なし |

灰色の死んだカードにしない。絶対上限ではカード自体を消す。

追加後に総席数が160を超える場合（例: 既存159席相当で定員4の卓を足す）もカードを出さないか、タップでハード上限。再生ボタンは出さない。

### 3.5 会場設定（列／行）

- ピッカーは回している最中にダイアログを出さない。出すのは **適用時だけ**（現行列の挙動を維持）
- 範囲は `1...FeatureLimit.maxColumnCount`（行を入れるなら `1...maxRowCount`）
- 注意文は1行に統合する。列用と行用を並べない

> 1〜2列・5行まではすぐ使えます。それ以上は動画1本で、この席決めのあいだ開きます。

行スライダーを今すぐ入れないなら、列だけの現行注意文を次に置換してよい。

> 1〜2列はすぐ使えます。3列以上は動画1本で、この席決めのあいだ人数・テーブルも含めて開きます。

### 3.6 ダイアログ文言

**人数（解放できる）**

- タイトル: `人数を増やせます`
- 本文: `無料では40人までです。動画を1本見ると、今回の席決めでは120人まで追加できます。`
- 主: `動画を見て追加する`
- 副: `あとで`（cancel）

**会場（列・行・卓で共通）**

- タイトル: `会場を広げます`
- 本文: `3列以上の配置や、テーブルを増やすには動画が1本必要です。見終わると、この席決めでは上限まで使えます。`
- 主: `動画を見て広げる`
- 副: `あとで`（cancel）

**絶対上限（人数）**

- タイトル: `これ以上は追加できません`
- 本文: `一度に扱えるのは120人までです。人数を減らしてから追加してください。`
- ボタン: `OK` のみ

**絶対上限（テーブル／総席数）**

- タイトル: `これ以上は追加できません`
- 本文: `一度に置けるテーブルは40までです。テーブルを減らしてから追加してください。`
- 総席数で先に当たった場合も同じタイトル。本文は `これ以上テーブルを増やすと表示しきれません。テーブルを減らすか、定員を下げてください。`
- ボタン: `OK` のみ

文言中の数字は `FeatureLimit` から組み立てる。View に 40 / 120 を直書きしない。コピーを `RewardedAdCopy` か、会場／人数用の小さな Copy 型に寄せて Share / VenueSettings / AttendeeList で再利用する。

### 3.7 動画成功後の再開（必須）

視聴成功 → `grantSessionUnlock()` → **元の操作を完了** → 親へ通知。解放だけして画面を閉じない。

| 元の操作 | 成功後にやること |
|---|---|
| 参加者＋（入力済み名前あり） | その名前を1件追加する。フィールドは空に戻す（現行の追加成功時と同じ） |
| 一括追加 | バッファに残した名前をすべて追加する（絶対上限で切る） |
| お気に入り読込 | バッファ分をリストへ流し込む。読込自体をやり直して先頭から40人にしない |
| テーブル追加 | 1卓追加する |
| 会場設定の適用 | 選択した列（と行）を適用し、シートを閉じる（現行の列適用と同じ） |

キャンセル / 未獲得 / 失敗: 何も足さない、列も変えない、バッファは残してよい（再タップで同じダイアログ）。バイパスフラグは立てない。

リワード提示中に親 View の `onDisappear` が来ることがある（現行 VenueSettings の hotfix と同じ）。提示中は running task を殺さない。視聴完了後の適用を消さない。

### 3.8 初期テーブル生成との関係

座席表入場時、`buildInitialTables()` は人数と `defaultCapacity` から卓数を決める。

- 無料未解放でも、人数≤40 なら必要な卓（最大10）を自動生成してよい。入場直後に会場拡張ダイアログを出さない
- 人数41...120で未解放、は参加者リスト側で既に止めているので、この経路には来ない（リストで先に解放するか、40人までしか入れない）
- 自動生成が内部キャップ160を超える場合は、定員を維持したまま卓数を `maxTotalSeatCount / capacity` で切り、余った人は現行どおり「席不足で配置されない」既存仕様に従う。ここで広告は出さない

## 4. VIPER 実装時の注意点

広告基盤の規約（`refactor_Ad.md` / `refactor_seating.md`）を崩さない。バナーを5層モジュールにしない。リワード提示は Router、要否判断は Interactor。

### 4.1 層の責務

| 層 | やってよいこと | やってはいけないこと |
|---|---|---|
| View | ボタン見た目、ダイアログ提示、`RewardedAdCopy` / 本仕様の文言表示 | `FeatureLimit` 以外の数字直書き、`GoogleMobileAds`、`isSessionUnlocked` の独自判定 |
| Presenter | Route の切替、バッファ保持、成功後に元操作を再実行、Router へ提示依頼 | SDK の load / present、ユニット ID |
| Interactor | 上限判定、`UnlockRequirement`、`grantSessionUnlock()`、追加の実行 | SwiftUI / UIKit / 広告 SDK |
| Router | `presentRewardedAd()` のみ（既存 Share / VenueSettings / AttendeeList と同じ） | 無料／絶対の判断 |
| Gateway | `FeatureUnlockState`、`RewardedAdGateway` | View から直接参照 |
| Entity | `UnlockRequirement`、Copy、エラー | 新しい課金 case を増やして列／人数を別商品にしない |

Protocol existential を MainActor クラスが保持すると deinit で malloc abort する。Router / Interactor は現行どおり具象型（`FeatureUnlockState`、`RewardedAdGatewayBase`）で保持する。

### 4.2 `FeatureLimit` に足す定数

```swift
nonisolated enum FeatureLimit {
    static let freeTemplateCount = 3
    static let freeFavoriteGroupCount = 3

    static let freeColumnCount = 2
    static let maxColumnCount = 10

    static let freeRowCount = 5
    static let maxRowCount = 10

    static let freeTableCount = 10
    static let maxTableCount = 40

    static let freeAttendeeCount = 40
    static let maxAttendeeCount = 120

    static let maxTotalSeatCount = 160
}
```

`VenueSettingsInteractor.selectableRange` は `1...FeatureLimit.maxColumnCount` に置換する。行ピッカーを足すなら `1...FeatureLimit.maxRowCount`。

### 4.3 `FeatureUnlockState` の扱い

- インスタンスは増やさない。`SessionFeatureUnlock.shared` を座席表 Router 組み立て時に注入する現行経路を維持する
- 参加者リストは座席表より前にいる。人数解放も同じ `SessionFeatureUnlock.shared` を `AttendeeList` の assemble で注入する
- テストは `FeatureUnlockState(isSessionUnlocked:)` を直接渡す（現行 VenueSettings / SeatingChart テストと同じ）
- `grantSessionUnlock()` の呼び出し点を列適用だけに残さない。人数追加成功・卓追加成功・会場適用成功のすべてが、視聴成功後に一度呼べばよい（多重呼び出しは冪等）
- Share の画像／CSV 用に別フラグを足す場合（`v2.1_ExportAndPresentation.md`）、**別インスタンス**にする。`SessionFeatureUnlock.shared` を共用しない

### 4.4 `UnlockRequirement` は2値のまま

ハードキャップは解放条件ではない。Interactor の追加 API は例えば次のように分ける。

```
enum CapacityDecision: Equatable {
    case allowed                    // すぐ実行
    case requiresUnlock             // 動画（= UnlockRequirement.rewardedAd）
    case blockedHardLimit           // 広告なし拒否
}
```

`UnlockRequirement` に `.blocked` を足さない。Share の `imageShareRequirement()` が `.rewardedAd` 固定である契約を壊さない。

### 4.5 モジュール別の作業

**AttendeeList**

- Interactor: 人数の `CapacityDecision`。一括追加は「入れた分」と「溢れた分」を返す
- Presenter: 溢れバッファ（`[String]`）。現行お気に入りの `pendingFavoriteName` と同型。`didConfirmWatchAd` 成功後にバッファを流す
- View: ＋のバッジと disabled。ダイアログは Route
- お気に入り4枠目の動画経路（`grantOneTimeFavoriteSaveBypass`）は変更しない。人数上限ダイアログと混線させない

**SeatingChart**

- Interactor: 卓追加前にテーブル数と総席数を見る。`addTable()` が黙って足し続けない
- Presenter: `didTapAddTable()` が requirement を見て Route
- View: 追加カードの出し分け、再生バッジ
- `buildInitialTables()` で入場時ダイアログを出さない（§3.8）

**VenueSettings**

- 列の `applyRequirement()` を会場拡張判定に一般化。成功時 `grantSessionUnlock()` は現行維持
- noticeText / アラート文言を本仕様のコピーへ置換
- 行を入れるなら列と同じ Apply 経路。行だけ別 Router 提示を増やさない

**Share / FavoriteGroup / SeatingTemplate**

- 本仕様では機能追加しない。回帰だけ確認する

### 4.6 提示経路

新規の広告 SDK ラッパを作らない。現行:

- 要否: Interactor → `UnlockRequirement`
- 提示: Presenter → Router → `RewardedAdGatewayBase.present()`
- 未準備: `RewardedAdError.notReady` → `RewardedAdCopy`
- キャンセル / 未獲得 / 失敗: catch して解放しない（現行 VenueSettings / AttendeeList と同じ）

人数解放は `AttendeeListRouter` に既に `presentRewardedAd()` がある。経路を増やすならそれを使う。座席表の卓追加は `SeatingChartRouter` に同じ1行を足してよい。判断は Interactor に残す。

### 4.7 テストで固定すること

既存スイート（SeatingChart / VenueSettings / AttendeeList / Share）を回帰基準にする。追加する characterization:

1. 人数39→40は広告なし。41人目は未解放なら `.rewardedAd`、解放済なら追加される
2. 120人の次は `blockedHardLimit`。Gateway の present が呼ばれない
3. 列2は広告なし。列3は未解放なら広告。視聴成功後は列8も広告なし（現行テストの拡張）
4. 列3で視聴成功したセッションは、41人目も11卓目も広告なし
5. 卓10は広告なし。11卓目は未解放なら広告。40卓の次と総席数160超はハード。present されない
6. 一括追加で溢れをバッファし、視聴成功後に残りが入り、失敗後は入らない
7. 画像共有は従来どおり独自の `UnlockRequirement`。会場拡張フラグが立っても Share 側は変わらない（現行契約を壊さない）
8. お気に入り4枠目は従来の1回バイパス。会場拡張フラグでは4件目が保存できない

検証端末は既存計画と同じ（iPhone 17 / プロジェクト所定）。iOS 18.4 シミュレータの malloc abort 回避も現行どおり。

### 4.8 実装順（推奨）

1. `FeatureLimit` に定数を足す。列レンジを定数参照に置換する（挙動は変えない）
2. `FeatureUnlockState` のコメントと、列判定を「会場拡張」に読み替える。人数・卓の Decision を Interactor に足す
3. AttendeeList の＋／一括／お気に入り読込。成功後再開を先に通す（入力が本業）
4. SeatingChart の卓追加とカード出し分け
5. VenueSettings 文言と、行を入れるならピッカー
6. 内部キャップ160を卓追加と初期生成に接続
7. 回帰 + §4.7

Phase を跨いでも、広告 SDK と `SessionFeatureUnlock.shared` の寿命は触らない。

## 5. 受け入れ条件

- 40人・2列・10卓では、バナー以外の動画が出ない
- 41人目 / 3列適用 / 11卓目のどれか最初の1回だけ動画が出る。成功後、残り2種は同一起動中に広告なし
- 動画成功後、ユーザーが押した操作が完了している（名前が入る、列が当たる、卓が足される）
- 120人、40卓、総席数160では再生ボタンが出ない
- 無料中に残数カウンタが出ない
- 画像共有とお気に入り4枠目の既存挙動が変わらない
- 座席表入場だけで会場拡張ダイアログが自動表示されない
